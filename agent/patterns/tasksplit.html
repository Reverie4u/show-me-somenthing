LLM任务拆分

把大任务切成小步骤，每步只做一件事。核心原因不是“直觉”，而是 context window 有限：任务越大，中间状态越多，越容易出错。

PART 01 · 为什么

“桌面太乱”才会出错

context 能同时装的东西有限

搜索结果、推理、半成品全都堆在一起，模型很难持续追踪“我现在在做哪个子目标”。拆开后每步聚焦一件事，桌面干净，质量更高。

出处：context window 有上限、Agent 需维持状态完成多步工作，见 Anthropic《Building Effective Agents》（官方）对 Agent 工作流与步骤的讨论，OpenAI 亦有类似官方 Agent 说明。拆成独立步骤还带来额外好处：每步可单独检查与重试，不必从头跑。
PART 02 · 怎么拆

两种思路：你自己拆，或让模型拆

静态拆分与动态拆分

区别在于“拆解这件事”由谁决定。

静态拆分动态拆分
决策开发者写死 WorkflowLLM 先输出计划再执行
可预测性高，行为确定低，灵活
风险遇到没设计的场景卡住计划质量不稳，一步错步步错
对应范式固定编排Plan-and-Execute
注意：CoT / ToT 说的是“LLM 内部怎么把一个复杂问题想清楚”，静态/动态拆分说的是“Agent 怎么把大任务切成多个独立执行步骤”，两者粒度和目标不同。
PART 03 · 并行

识别依赖，能并行的并行

只降关键路径，不降每步

把步骤画成有向无环图（DAG），无依赖的步骤并发跑，总时间由最长路径决定。

依赖示意
步骤1 ──┐
　　　├──> 步骤3 ──> 步骤4（最终输出）
步骤2 ──┘
效果：依赖稀疏、工具 I/O 占主要耗时的时候，端到端延迟可显著下降；若所有步骤强依赖上一步，并行空间为零。
PART 04 · 粒度

以“原子操作”为单步标准

不是越细越好

太细会多很多调用、且步骤间衔接生硬；太粗又回到桌面乱、无法定位。

原子的

边界清晰

只做一件事、有明确输入输出、不依赖其它步骤。判断法：能给它写个清晰函数签名吗？

验收标准

可验证

每步拆分时配好“验收断言”，如“输出必须含价格数字与计费模式”，便于自动检查与重试。

自适应

做不好就再拆

执行器做不好某步时，交给规划器继续拆细；做得好的步骤一步到位，成本与实际难度成正比。

Replan：执行中若发现结果让后续计划失效，把已完成结果 + 剩余计划交给规划器重新规划，保证计划与实际同步。
