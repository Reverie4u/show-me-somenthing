ZSet —— 带着分数排队的集合

PART 01 · 是什么

ZSet 概述

成员唯一,分数任意(可重复),按分数天然有序

score 类型是 double(实数),成员是字符串。整个集合始终处于「按 score 升序」状态——不需要你 sort。

语义命令
写入ZADD(可批量) · ZINCRBY(给分数加数)
精确查ZSCORE / ZMSCORE · ZRANK(升序名次) · ZREVRANK
范围遍历ZRANGE / ZREVRANGE · ZRANGEBYSCORE / ZREVRANGEBYSCORE · ZCOUNT · ZLEXCOUNT
弹出ZPOPMIN / ZPOPMAX · BZPOPMIN / BZPOPMAX(阻塞版)
删除 / 计数ZREM · ZCARD
score 是 double:别用来精确计数。float 的整数上限是 2^53,超过就会丢精度——zset 用于「排名/时间戳」是安全的,用于「精确库存/ID」不是。
PART 02 · 编码

listpack → skiplist + dict

切换条件与双结构

小对象 · listpack 编码大对象 · skiplist + dict 双结构
结构 连续内存,元素轮流是 [member][score]…… 跳跃表 + 哈希表,两个独立结构同时持有全部成员
触发 zset-max-listpack-entries(默认 128)且 zset-max-listpack-value(default 64 B) 任一超出
ZRANGE 家族 线性扫 listpack——n 小等于白给 跳表横走 O(log n + m)
ZSCORE(按 member 查) 线性扫 dict 直接命 O(1)

注意:zset 没有「只跳表」或「只 dict」的版本——大 zset 永远是跳表(顺序)+ dict(精确)双持有,这一点和 hash 的「二选一」不同。

PART 03 · 跳表

skiplist:概率换来的平衡

分层链表,赌出来的对数

底层是一条完整有序链表;每层各带几根「跳过中间节点」的长指针,让查找从「一步步走」变成「一层层跳」。第 1 层概率上遍历 2 次就知道「往下走还是横着走」。

↑ 查找 15:从 L4 走到 7 → 下一格直接是 19(太大,降层)→ L3 走 7 → 11(下一格过大,降层)… L1 上从 11 走到 15。一眼:降层次数 ≈ 层数 ≈ log n
「概率平衡」是怎么来的:插入时抛硬币——正面加一层,50% 概率一层、25% 两层……严格说是 p=1/4 的几何分布(Redis 用 ZSKIPLIST_P = 0.25,ZSKIPLIST_MAXLEVEL = 32)。每个节点层数随机,「长指针多的人自然爬得高」,期望上每层节点数减半。

查找

O(log n) 均摊

从最高层开始,向右看:下一格不超过目标就走,超过就降一层。期望跳 1/p 次/层——这是「概率结构」最优雅的抽样。

范围查询

O(log n + m)

找到起点后,直接沿底层链表顺序走——这是跳表对自己最大的奖赏:ZRANGEBYSCORE 没有任何额外结构,就是「链上散步」。

span + ZRANK

排名就是攒跨度

每层指针存 span(跨过多少节点),查 ZRANK 时从左往右累计 span——排名 O(log n),不需要数一遍。

1为什么是 skiplist 而不是红黑树/跳表?antirez 的选择

假设换成红黑树/B 树也能做「有序集合」——但跳表赢在三个「适合本场景」的点:实现与调试远比平衡树简单(就是普通链表加概率分层);范围遍历无需中序遍历状态机,找到起点沿链走即可;期望 O(log n) 对 Redis 的规模绰绰有余。antirez 在问到这一选型时反复强调的正是「简单、可调试、正好合适」——这大概是 Redis 整个项目的选型美学。

选「简单」而不是选「最强」:平均时间复杂度相同的地方,可维护性优先。
PART 04 · 双结构

一个 zset,两套数据

跳表负责「按分数走」,dict 负责「按成员找」

一次 ZADD 会写两处
zsl——▶
skiplistscore → member
ht——▶
dictmember → score
…同一次分配区域
↑ 每个 value 的 robj 里 encoding=SKIPLIST,ptr 指向 zset { skiplist* zsl; dict* dict; }
拆开看两个结构的「分工」
skiplist · 序ZRANGE / ZRANGEBYSCORE / ZRANK / ZPOPMIN —— 一切「按排名」的操作
dict · 精确ZSCORE / ZMSCORE / ZREM —— 一切「按成员」的操作;也保证成员唯一、O(1) 找分数
↑ 共同体:每个操作都先知道自己走哪个门——「按分数」走跳表侧的链,「按成员」走 dict 侧……这就是「两个都留」的代价与收益。
1为什么不能只留一个
  • 只有 skiplist:ZSCORE(按 member 查分数)得在跳表上逐个比较 member——成员字符串的字典序,每次 O(log n) 比较 + 内存两跳,不快。
  • 只有 dict:ZRANGEBYSCORE 需要全量排序——想「从 90 分到 100 分」就得扫全部、排完再截,做不到。
  • 都要:一次写入双维护(两个结构都写或都删),ZADD 的常数翻倍——换来的是「ZSCORE 快 + ZRANGE 快」两全。Redis 只要 ZSET,这个成本它掏得起。
这就是「二选一」的反面教材——为了「按分数走」和「按成员找」双向都成立,zset 选择付一次双写(写两个结构)的常数成本。
PART 05 · 场景

使用姿势

场景与注意事项

都充分利用「按 score 序」这一天然顺序。

排行榜:ZADD ranks score member,ZREVRANGE 取 TOP-N 延迟队列:score 填执行时间戳;ZRANGEBYSCORE now now+∞ 取到期任务再删 最近动态:时间戳做 score,按时间范围取 统计报告:分桶直方图(score 作为桶索引)
延迟队列的常见问题
  • 「取出后谁删」:用 ZPOPMIN + BZPOPMIN 是唯一合理路径,先取再删的脚本会丢任务。
  • 成员与分数是「两份」:同一 member 更新分数,是双结构双写——若你 10000 个进程同时乱改分数,序列化问题自己排队。
