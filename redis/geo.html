Redis · GEO

GEO —— 坐标存进 zset 的分数

它不是一种数据类型。GEO 把 ZSet 当位置集合用：GEOADD 的经纬度被编码成一个 52 位整数 geohash，作为 score 塞进 zset——排序、区间、查找全复用 zset 的现成机制，命令层负责换算距离与坐标。

PART 01 · 是什么

一组"地理语义"的命令

GEO 命令族

命令作用（一句话）
GEOADD key lng lat member …记录一个成员的坐标（可批量）；等同 ZADD key score member
GEOPOS key member…反解出成员坐标（已做过舍入，和存的可能差几毫米）
GEODIST key a b [unit]两个成员的地理距离（m/km/mi/ft）
GEOSEARCH key FROMMEMBER a BYRADIUS 5 km方圆 5 km 的成员（6.2+；也可 FROMLONLAT / BYBOX 矩形）
GEOHASH key member…输出标准的 11 位 base32 geohash 字符串——给其他 geo 库用
GEORADIUS / GEORADIUSBYMEMBER老写法（6.2 前的接口），语义同 GEOSEARCH；官方推荐新命令
和 zset 的关系——这不是比喻，就是同一个值：GEOADD locations 116.4 39.9 "天安门" 之后，ZRANGE locations 0 -1 能看到"天安门"，ZRANK、ZREM、ZINCRBY 都能操作它——因为成员还是那个成员，score 在 GEOSEO 里没有特殊旗子。
PART 02 · 编码

经纬度 → 52 位整数

位交错：geohash 的本质

经度 [-180, 180] 和纬度 [-85.05, 85.05]（墨卡托裁剪，Redis 的限制）各按 26 位 二分编码，然后经度位、纬度位交错拼成 52 位整数——这个整数就当作 zset 的 score。

52 位 = 经 26 + 纬 26,交错排列
位 51经0
位 50纬0
位 49经1
位 48纬1
…
↑ 前缀相同的两个 geohash,地理上也一定在一个矩形里——这叫"空间填充曲线",让"相距近"变成"数字相邻近"。它是"用 zset 做地理索引"的根
为什么偏偏 52 位?——为了精度与"不丢位"
经度 26 位 → 360°/2²⁶ ≈ 5.4×10⁻⁶ 度 ≈ 0.6 m　·　纬度 → 0.3 m 量级——够了(半径查询以外,50 位 舍入也会丢失 10 米内的信息)
↑ 更深一层：zset 的 score 是 double，其尾数恰好 52 位——用 52 位整数当 score，每一位都不会被 double 舍入吃掉。这个"52"是设计者算过的。
PART 03 · 查询

半径查询：粗筛 + 精算

GEOSEARCH 内部是怎么"只查圆内"的

zset 只有 score 一个维度——而 geohash 的交错意味着"半径查询"不能真的沿曲线数。Redis 的做法是两步：

1

按分数窗口粗筛

以查询点为中心,把"半径 × 地球尺度"换算成一个 geohash 边界框:8 个角点算出 score 区间 → ZRANGEBYSCORE 拉出候选成员。这步只排除"地理上显然不在"的。

2

逐个算真实距离

对候选成员 GEODIST(球面 Haversine 公式)计算真距离,dist ≤ radius 才留下。注意:

geohash 边界框不会让"精确性太差"——但它不会横跨地球;极地/跨 180° 经线会出坑
两次筛选
粗筛score 窗口
精算Haversine
结果成员 + 距离排序
↑ 真实距离不存任何地方(它们每回都重新算)——查一次算一次,地理查询的"O(log n + m)"就是这个意思。
为什么不能"只用 score 排+切"?因为 geohash 曲线沿单个数字跳变——"北京次中心"和"上海郊区"谁的 score 远离?分不清。所以地理这类需求,数据索引维度(score)与查询维度(距离)天生差一维,才会逼着做"粗筛+重算"。
PART 04 · 边界

注意这些细节

位置精度

坐标被舍入

GEOPOS 返回的是"编码再解码"的坐标——与存入值差零点几米(编码精度≈0.6 m×0.3 m 单元)。对线下场景无感;但"精确到登录 IP 库"这种输入,别把 geohash 当无损坐标。注:latitude 被裁剪在 ±85.05°。

小心 Z* 命令

同 key, 两套解释

geohash 坐在 zset 的 score 上——ZRANGEBYSCORE 会按它排逻辑序(不一定是地理序!),ZINCRBY 甚至能"扭曲"成非标准地理编码。GEO 与 Z 命令共存但语义分家,忘掉就乱了。

大半径查询的费用

粗筛挡不住太多

半径 5000 km 时边界框接近全图——粗筛基本失效,退化成"全集合扫描 + 逐个距离"。数据量大于十万时,记得按城市/区域分 key + 应用侧合并,或者直接上专业地理索引。

这页的"索引身份"小结

GEO = ZSet 上的一个视角。编码选择、双结构、持久化等 zset 的一切它全继承——所以没有独立结构页：读 zset.html 就是读 GEO 的内部。
