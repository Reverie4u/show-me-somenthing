Redis · SDS

Simple Dynamic String

SDS —— Redis 中字符串的底层实现。所有的键、绝大多数的值、AOF 缓冲区与客户端缓冲区，最终都由它承载。它是一个「长得像 C 字符串，但自带元数据」的动态字节数组。String 类型（类型页）只是它最大的客户。

PART 01 · 痛点

为什么 Redis 不直接用 C 字符串

C 字符串的三个直接痛点

C 字符串用 \0 作为结尾标志，简单但有三处硬伤；SDS 的头部三行元数据恰好逐一对应解决。

C 字符串的问题SDS 的机制
求长度 strlen() 要遍历到 \0，O(n) 头部直接存 len，取长这行代码是 O(1)
无法存储含 \0 的二进制数据（图片、序列化对象） 不看 \0，以 len 界定边界，二进制安全
strcat 不检查空间，可能越界写；每次追加都 重分配内存 写入前检查 alloc - len，不够先扩容再写；预分配 + 惰性释放 摊销 O(1)

不止 strcat：C 字符串函数族的问题

strcat 只是最先暴露的一个——整个 C 字符串函数族共用同一个病根：长度不是字符串对象的一部分，任何边界知识都只能靠末尾那个 \0 现推。以 \0 为唯一边界，催生出四类问题。

维度中弹的函数根因SDS 的解法
长度strlen 靠遍历找 \0，O(n)；内存里若根本没有 \0 还会越界读 len 字段 O(1)
写入strcpy / strcat / sprintf 不知道目标还剩多少空间——容量知识在调用者手里却不传递，写爆 alloc 字段 + 写入前检查
边界strcmp / strstr / strchr 遇到 \0 提前停，比较与查找的范围比你以为的小 按 len 界定，不认 \0
状态strtok 用静态指针保存遍历进度——不可重入、非线程安全，并发下结果不可预测 无状态，任意并发
1strlen 的隐藏成本：strcat 自己也在调它

strlen 不止自己 O(n)——看看 strcat 的源码，它内部就藏着一个 strlen：

char *strcat(char *dest, const char *src) {
    size_t dlen = strlen(dest);  // 先从头扫一遍 dest 找尾巴
    memcpy(dest + dlen, src, strlen(src) + 1);
    return dest;
}

于是循环里连续 strcat n 次，每次都要重扫一份从头开始增长的 dest——O(n²)。SDS 的 sdscat 直接读 len 定位尾部，均摊 O(1)。这是两者性能拉开差距的第一个点。

2strncpy：名字像安全函数，其实不保证 \0

听名字像"限制拷贝长度"，实际上语义源自 1970 年代 UNIX 目录项的烂设计：

char buf[8];
strncpy(buf, "hello, world", 8);  // 拷 8 字节，最后一位还是 ' '，没有 \0！
printf("%s", buf);                // 未定义行为：继续读 buf 后面直到撞见 \0
  • 不保证 \0 终止——n 字节塞满就没有哨兵，后续任何函数全部跟着失效
  • 源短时**用 \0 填充**补满 n 字节——性能白扔，填充是 memset 的活
  • 源长时**静默截断**——不报错、不提示
Linus 曾直言 strncpy 是"历史遗留的垃圾"；后来 BSD 才给出 strlcpy：始终保证终止、截断可检测
3strcmp：遇到 \0 就提前缩水
strcmp("abc\0def", "abc") == 0   // 返回相等——但两个串明明不同！

第一个 \0 就停，所以含内嵌 NUL 的序列（图片、序列化对象、协议数据）比不了，还可能越界读。二进制数据的正确姿势是逐字节：memcmp(buf1, buf2, len) + 长度先行判断——这正是 sdscmp 干的事。

头部三行元数据，各自解决一件事

结构体定义（src/sds.h），注意 __packed__：取消内存对齐，字段紧密排列、头部尽量小。

len

uint8_t · 已使用字节数（不含 \0）

O(1) 取长度的来源。也决定了数据的真实边界 —— 哪怕中间有 \0，也只认 len，这就是二进制安全。

alloc

uint8_t · 已分配容量（不含头部与 \0）

「还能追加多少空间」随时可见：alloc - len 就是剩余量。追加前先检查，不够就扩容再写，天然避开缓冲区溢出。

flags

uint8_t · 低位 3 bit 标记类型

标记这是一块 sdshdr5 / 8 / 16 / 32 / 64。按字符串长度自动选最小头部，让 "cat" 和 10MB 的字符串都不过度浪费。

头部大小随类型而变，buf 紧跟在 flags 之后 —— 代码里用 char buf[] 柔性数组，头部和数据同一次分配、连续内存，缓存友好。

一次追加：预分配怎么运作

字符串 s（sdshdr8）当前是 "hello"，执行 sdscat(s, " world")：

1

检查剩余空间

alloc - len = 5 - 5 = 0，而要追加 6 字节 —— 不够，需要扩容。

2

按规则扩容（sdsMakeRoomFor）

newlen = 5 + 6 = 11，小于 1MB，所以 newlen = 11 × 2 = 22。

分配：头部 3 B + 数据 22 B + 哨兵 \0 1 B
3

写入，更新元数据

alloc = 22，len = 11，数据写进 buf，末尾补 \0。

剩余 11 字节 —— 之后哪怕再追加 11 个字符，也零分配零拷贝
sds sdsMakeRoomFor(sds s, size_t addlen) {
  if (sdsalloc(s) - sdslen(s) >= addlen)
    return s;          // 剩余够用：直接返回，零分配

  newlen = sdslen(s) + addlen;  // 需要的最小长度
  if (newlen < 1MB)
    newlen *= 2;                // < 1MB：翻倍扩容
  else
    newlen += 1MB;              // > 1MB：每次固定 +1MB

  // 重分配内存 → 抄数据 → 迁移头部
  return new_sds_hdr(newlen, s);
}
逐次追加在最坏情况下仍是 O(n)（扩容要搬数据），但翻倍策略让「上一轮多留的空间」覆盖接下来若干次追加 —— 均摊下来每次追加是 O(1)，代价是偶尔一次 O(n)。

五种头部：按长度自动选择

同样的逻辑，针对不同长度的字符串用不同的字段宽度 —— 这也是「元数据有成本」的最终解法。sdshdr5 比较特殊：长度直接存在 flags 的高 5 位（最多 31），不单独占字段，且不可扩容 —— 一旦需要追加，就地升级成 sdshdr8。

sdshdr83 B1 + 1 B255绝大多数键值

「惰性释放」是预分配的另一面：sdsclear() 只把 len 清零、留下空间，真正释放内存要等显式 sdsRemoveFreeSpace() —— 频繁清空/重建的场景因此免掉大量分配与释放。

PART 03 · 答疑

延伸追问

两个常被追问的问题

看源码和面试里都会反复出现的细节。

Qstrcasecmp 是干什么的函数？

strcasecmp 是 C 标准库（POSIX）里的大小写不敏感字符串比较函数，与 strcmp 的唯一区别是忽略大小写（'A' 与 'a' 视为相等），返回 0 表示相等。

  • Redis 里用它干什么：比较命令名与协议参数——SET/set/Set 都是合法命令，cmd 查找就是 NOCASE 匹配。
  • 与 SDS 的关系：SDS 的 buf 末尾保留 \0，正是为了能直接把 s->buf 传给这类 C 库函数，免去先拷贝成真 C 字符串。
  • 局限：它比较到第一个 \0 就停，所以只适合纯文本。含二进制（如存了图片）的 SDS 要用 sdscmp——按 len 逐字节比较，不看 \0。
Q为什么 sdshdr5 的 len / alloc 编码在 flags 高 5 位？

先纠正一个措辞：len 编码在 flags 高 5 位；alloc 这个类型根本不存在。sdshdr5 的完整头部只有一个字节：低 3 位存类型，高 5 位存长度。

+----------------+------------------+
| 高 5 位 (len)   | 低 3 位 (type)    |
| 0..31          | SDS_TYPE_5 = 0    |
+----------------+------------------+
  • 动机：短字符串占绝对多数。头部从 3 字节（sdshdr8）变成 1 字节，在数亿个 key 上是数百 MB 级别的差距。
  • len 占的是 flags 里空出来的位。无论哪种类型，标识类型的 flags 字节都存在；低 3 位放类型（5 种类型 3 位够用）后，高 5 位空着也是空着——于是长度有了零成本存储，头部总量仍是 1 字节。
  • 为什么上限是 31：5 位二进制最大值就是 31，是自然边界，恰好覆盖绝大多数 key/value 的短字符串。
  • 代价：一个字节装不下 alloc，sdsalloc() 对它返回 0（剩余空间恒为 0，不可扩容）。一旦 append，sdsMakeRoomFor 直接把整个字符串升级成 sdshdr8（3 字节头部），之后不会再降级。连 sdsclear 都有特殊分支：长度存在 flags 里没法原地清零，只能 sdsnewlen("", 0) 新建空串。
PART 04 · 位置

SDS 在 Redis 中的位置

SDS 出现在哪里

记住这些位置，就明白两件事：为什么 key 没有编码、为什么二进制安全如此重要。

所有 key String 类型 value（embstr / raw 编码） list / hash / zset 的底层元素（如 hashtable 编码） AOF 缓冲区 客户端输入 / 输出缓冲区 命令名比较
与 String 类型的关系（一句话版）

String 类型是语义层：robj.type = OBJ_STRING + 编码（int/embstr/raw）。SDS 是物理层：embstr/raw 两种编码的 value 直接就是一块 SDS。int 编码的值（纯数字）是唯一的例外——唯一不经过 SDS 的 String。完整关系图（四层穿透）见 string.html，对象外壳见 obj.html。「为什么 String 必须是一段字节数组」背后的答案就是本页 PART 01 的二进制安全：一个字节都不得变形。
