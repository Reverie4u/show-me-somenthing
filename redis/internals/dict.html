Redis · dict

dict —— Redis 的哈希表

整个数据库的主键空间就是一张 dict；hash / set / zset 的大对象编码也各有一张。它的看家设计是渐进式重哈希——单线程服务器一边跑命令一边慢慢搬桶，绝不一口气搬完把服务器卡住。

PART 01 · 为什么

O(1) 查找的代价

把「找」变成「算」

链表找 key 是 O(n)；dict 的做法是：算一个哈希值 → 对表大小取模 → 直接跳到桶位。桶位里有链表，把同桶的键从链头上一个个比过去。

get(key):
    hash = SipHash(key, random_seed)   // 带随机种子，防哈希碰撞攻击
    idx  = hash & sizemask              // 表大小永远是 2 的幂，等价于取模
    桶位 = table[idx]
    返回 链表中「key 相等」的节点         // 均摊 O(1)，最坏 O(n)

链地址法解决碰撞

每个桶位是一条链表

两个 key 落在同一桶时，后者头插进链。查找时顺链比较——因此查找时间是「O(1) + 当前链长」。

负载因子决定何时扩容

used / size

桶位不够时链变长、退化成链表。Redis 用「负载因子 ≥ 1 就翻倍」的策略尽早扩容，把链长控制在个位数。

单线程的特殊约束

一次 rehash 不能卡顿

如果 100 万个 key 要换新表、一次搬完，会锁住事件循环几十毫秒——对单线程服务器这不可接受。于是有了 PART 04 的渐进式。

PART 02 · 结构

三级容器

dictEntry → dictht → dict，再套一层「双子表」

typedef struct dictEntry {
    void *key;                    // 实际是 SDS（见 sds.html）
    union { void *val; uint64_t u64; int64_t s64; double d; } v;
    struct dictEntry *next;       // 链地址法
} dictEntry;

typedef struct dictht {
    dictEntry **table;      // 桶数组，每个元素一条链
    unsigned long size;       // 桶数，恒为 2 的幂
    unsigned long sizemask;   // size - 1，与哈希值做 &
    unsigned long used;       // 已存元素数
} dictht;

typedef struct dict {
    dictType *type;                // 函数指针：hash/compare/keydup...
    dictht ht[2];                  // 【关键】两份，一份在搬迁、一份在生长
    long rehashidx;             // 重哈希进行到第几个桶；-1 表示未进行
} dict;
ht[2] 是理解全部 dict 行为的钥匙：重哈希期间两张表同时工作——旧表在「消费」，新表在「积累」。
查找路径：dict → ht(第 0 张表) → 桶位 → 链

PART 03 · 扩容

翻倍与收缩的规则

扩容、缩容的时机

动作触发条件新大小
空表初始化 首次插入 key DICT_HT_INITIAL_SIZE = 4 桶
扩容 used ≥ size（负载因子 ≥ 1）
但处于 BGSAVE/BGREWRITEAOF 时放宽为 used/size > 5（避免子进程拷页时内存抖动）		 翻倍：used × 2 向上取 2 的幂
缩容 serverCron 里检查：used × 100 / size < 10 且 size 大于初始值 缩到 used 的 2 的幂（不小于 4 桶）
「负载因子 > 1 才翻倍」意味着平均链长已 略大于 1：查找要迈 1 步半。但对比一下：负载因子允许升到 0.75 就翻倍的设计（Java HashMap），Redis 的桶用得更狠——因为它有渐进式重哈希兜底，不怕桶位紧张。
PART 04 · 渐变

渐进式 rehash：一次搬一桶

把一次「大搬家」摊进每一条命令的时间片里

假设从 16 桶扩到 32 桶、100 万条记录——如果命令循环里一次性搬运，Redis 会卡住毫秒级（触发客户端超时）。渐进式做法是：每条命令执行前后，搬一小批桶，直到搬完。

1

配好新房，只租不搬

触发扩容：新建 ht[1]（32 桶）rehashidx = 0。此刻一个桶都还没搬，但表已经「扩容成功」——新一轮插入可以直接进新房。

2

每次命令，搬一挂

每条命令执行时调用 dictRehash(d, 1)：把 ht[0] 的 rehashidx 桶整条链搬到 ht[1]，然后 idx+1；每轮耗时上限 1ms（dictRehashMilliseconds），由 serverCron 兜底。

3

这期间，函数们如此行事

「查」看图双方：先查 ht[0]，没找到再查 ht[1]；「增」只写 ht[1]；「删/改」两边都处理。逻辑像搬家过程——要找的东西可能还留在旧家，也可能已在新的。

4

搬家结束

全部桶搬完：ht[0] = ht[1]，ht[1] 清空待命，rehashidx = -1。下一次扩容重新走这套。

搬家中的瞬间（ht[0] → ht[1]）
ht[0] · 旧表已搬rehashidx 前的桶
ht[0] · 旧表待搬rehashidx 后的桶
ht[1] · 新表在积累迁移来的 + 新增
↑ rehashidx 是一个「搬到了第几桶」的进度指针，从 0 走到 size——只有一个 CPU，一切都要可暂停。
为什么单线程先想的是「可暂停」？因为 Redis 的事件循环里没有「阻塞一会儿再回来」的说法：一次 rehash 若耗时 50ms，客户端就会看到一次 50ms 的延迟毛刺——把它拆成 1000 次 × 0.05ms，毛刺消失，代价仅是每条命令多搬几个桶的 CPU。
PART 05 · 应用

dict 在 Redis 中的义务

dict 在 Redis 中的主要用场

数据库主键空间（所有 key） 过期键字典 hash 的 hashtable 编码 set 的 hashtable 编码 zset 的 member→score 侧 pub/sub 频道 · Lua 脚本缓存等等
主键空间是 dict，value 是 robj

dictEntry.key = key 的 SDS，dictEntry.v = 指向 robj 的指针。EXISTS/DEL/TTL 全部发生在这一层；对值做的 GET/LPUSH 等则先经过它、再进 robj 的 ptr。所以一条命令的完整路径是：dict 找 key（约 O(1)）→ robj 分派 type → encoding 决定如何操作数据——三层，一次往返。

历史注脚：Redis 曾经把「字典」写成 HT 编码，所以 hash/ set 的大对象编码名落地成 OBJ_ENCODING_HT——名字是时代的化石，但读源码时会一直看到它。
