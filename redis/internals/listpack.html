Redis · listpack

listpack —— 紧凑编码的现代方案

小 hash、小 zset，以及 quicklist 的每个节点，都用这一块「一行内存」承载：无指针、连续存放、每个条目 1~9 字节。它是 ziplist 的换代产品——7.0 起全面接管了 ziplist 的岗位，且修掉了后者最著名的 bug：连锁更新。

PART 01 · 为什么

指针太贵

一个 entry 的两种成本对比

dict 的每个 entry 至少一个指针 + key 指针 + value 指针 + 链表 next——8 字节一个。一个存 3 个字段的小 hash，用 dict 就是几十字节只为「指针结构」付钱；listpack 把同样的数据摊进几乎不浪费的字节里。

dict（hashtable 编码）listpack
一个元素占地 dictEntry（~48 B）+ robj + 数据指针两跳 编码 + 数据 + backlen，个位 + 数据字节
内存形态 一堆独立小对象，四处零散 一块连续缓冲，线性扫读
查找一个元素 哈希 O(1)（均摊） 线性扫描 O(n)——小 n 无所谓
适用规模 大集合：命中随机性高，哈希有规模效益 小集合：n 上几十个，扫描反而更划算

于是规则是：小→紧凑编码（省内存，够快），超过阈值→哈希表（提速）。阈值本身见各类型页（hash-max-listpack-entries 128 等）。listpack 就是「小」这一侧的答案。

PART 03 · 编码

前缀位模式全表

看第一个字节，就知道这条目是啥

来源：src/listpack.c（7.2）。编码字节的前几位像指纹——从不重叠，所以任何位置都可以「按字节看」还原出条目。

第一字节位模式类型取值条目体
0xxxxxxx7 位无符号整数0 ~ 127仅编码字节本身
10xxxxxx6 位字符串长度 0 ~ 631 + len
110xxxxx13 位有符号整数-4096 ~ 40952 B
1110xxxx12 位字符串长度 64 ~ 40952 + len
1111000032 位字符串长度 ≥ 40965 + len
1111000116 位有符号整数-32768 ~ 327673 B
1111001024 位有符号整数-8388608 ~ 83886074 B
1111001132 位有符号整数±2³¹5 B
1111010064 位有符号整数long long9 B
11111111协议级 EOF——1 B
一个例子：写入 "apple" 和 42 
lpAppend(lp, "apple", 5);
lpAppend(lp, (unsigned char*)&lval, sizeof(lval));   // 先编码为整数入口

"apple"： 10xxxxxx(101) | 'a' 'p' 'p' 'l' 'e' | backlen
42：     0xxxxxxx(0x2A) | backlen

42 是 0~127 直接进 7 位编码——一个字节就存下了；而它在 SDS 里是 2 字节字符 + 3 字节头部 + 1 字节 \0。小数字等于白拿：没占什么额外位置。

编码方向的取舍：插入时先试「能否转整数」——"42" 字符串会先被 lpStringToInt64 试转；能则按整数编码存，省去直接存字符的字节。代价是整数取出后再读回字符串，命令层自动完成。

PART 04 · 逆行

backlen：倒着走回家的钥匙

每个条目都「记得自己多长」

前向遍历简单：编码字节自带长度，读完一个条目就落在下一个入口。问题在逆向遍历——只有一块连续内存、没有指针时，怎么从上一条目跳回来？

1

条目末尾写 backlen

backlen = 该条目「编码 + 数据」的总字节数，1~5 字节变长。写入时是反序 + 高位续接符：从末尾读，第一个最高位为 0 的字节说明完了。

2

逆序遍历

从 EOF 前最后一字节往左读 backlen → 得到最后一条的长度 → 指针倒扣即可跳到前一条。如此反复，每次跳跃 O(1)，无需任何全局索引。

3

巧合的自足

backlen ≤ 5 字节可表示 ≤ 268 MB 的单个条目，低于 listpack 总长上限（4 GB）——于是任何合法 listpack 都支持逆行：每个条目都记得自己多长。

逆序跳跃示例
elem210B
backlen[10]
elem122B
backlen[22]
EOF
↑ 从 EOF 前出发：左移读到 [22] → 回到 elem1 起点；想再往前读 [10] → 上一条 …
为什么反向遍历有名字：LRANGE 取末尾的逆序段、小 zset 的 ZREVRANGE、hash 从尾部删字段——都踩在「读 backlen ← 回退」这一套动作上。
PART 05 · 替代

ziplist 的连锁更新为什么就此消失

同一个目标，两个时代的答案

ziplist（旧，已淘汰）同样紧凑。它把长度存在条目开头（prevlen：前一条目的长度）；listpack 把长度存在条目尾部（backlen：自己多长）。这一字之差，一场灾难。

ziplist（老）listpack（新）
长度存在哪 条目开头：prevlen，记录上一条多长 条目尾部：backlen，记录自己多长
改一个条目 自己变长 → 下一条的 prevlen 字段变了 → 下一条也变长 → …连锁更新（最坏整块重写） 只改自己的 backlen，其余条目无感
逆向遍历 先读 prevlen 再扣——链条即迭代 读 backlen 直接跳，同样 O(1)
1连锁更新的根因：边界扩大

ziplist 的 prevlen 是变长字段：长度 < 254 用 1 字节，否则 5 字节。假如有个 252 字节的条目，把它改大 → 超过 254 → 下一条目的 prevlen 从 1 字节变大到 5 字节（这个条目自己也变大了）→ 它的下一条的 prevlen 又要重新计量 → 若恰好都在临界值附近，整个 ziplist 的后续条目全部重写。这就是「连锁更新」：一次普通 APPEND，最坏 O(n) 全量重写。

概率低（临界点条目极少）但崩溃放大器极狠。listpack 从设计上铲除了它：每个条目只关心自己的长度，改动局部发生，不传播。
时间线：ziplist 承担了 hash/zset/list 小对象编码近十年；listpack 于 Redis 5.0 引入（先用于 stream、quicklist 内层），7.0 全面接管 hash / zset 小对象；ziplist 进入「历史兼容」状态。为什么快十年才换？紧凑编码的正确性成本极高（每个字节位模式都得向后兼容），zset 的 RDB 格式老版本还在读——兼容债，偿还需耐心。
PART 06 · 应用

listpack 在 Redis 中的位置

hash 的小对象编码（hash-max-listpack-entries 128, value 64 B） zset 的小对象编码（zset-max-listpack-entries 128） quicklist 的每个节点（list 的底层） Stream entry 组（逐步部分）
它和其他结构的分工
  • 与 dict 的分界：listpack 用于「线性可容错」的小规模场景；超过阈值换 dict——见 hash.html 与 zset.html。
  • 与 SDS 的关系：listpack 存元素（字段名、字段值、member、score），不是存整个字符串对象。每个小值以「编码字节」微格式内嵌，没有 robj、没有 SDS 头——这是它省内存的本质。
  • 与 quicklist 的关系：quicklist 是「链表外套 + listpack 内核」，节点即一块 listpack——见 list.html。
