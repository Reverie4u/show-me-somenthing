Redis 数据类型与底层结构

一套笔记,两条路径:类型页讲「它是什么、怎么用、什么时候换编码」,结构页讲「这个结构怎么设计、为什么敢这么设计」。底层有共享部件——类型是入口,结构是资料室。

全景矩阵

类型 × 编码 × 结构

一句话版本：String 与 List 只有一个编码方案；hash / set / zset 是「小对象省内存、大对象提性能」的两阶段方案；bitmap / HLL / GEO 不是新类型，是把 String 与 ZSet 换了个解释；Stream 是真正的第六种类型。

类型页

以用户数据类型为主干

String

三种编码 · 与 SDS 的关系

最常用的类型：int 数字内联、embstr 短串同块、raw 长串分离；四层路径讲清「String → robj → 编码 → SDS」一条链。

List

quicklist · 双向链表 + listpack

头尾 O(1) 的队列。为什么「链表 + 连续块」的组合是 list 的正确形态；两个可调旋钮（填充 / 压缩）。

Hash

listpack → dict 两阶段

字段级操作的映射。小对象几乎零额外开销（连续内存），大了靠哈希提速；切换单向不缩回。

Set

intset → dict 两阶段

无序不重复的集合。intset 是「一个整数一字节」的有序数组，带二分查找与一次性升级。

ZSet

listpack → 双结构

带分数的排序集合。skiplist 管顺序、dict 管精确——五类型里最贵的一次双写。

扩展页

基于类型的视图与第六类型

bitmap / hyperloglog / geo 不是 `type` 的新成员——它们只是现有类型的另一种用法；stream 是 5.0 起的真正新类型。

Bitmap

String 的位视图 · 非独立类型

一位一个索引位，用户 ID 映射到 offset：每日活跃 1.25 MB/千万用户；BITOP 算并集交集。

HyperLogLog

String 里的近似计数 · 非独立类型

基数估算：12 KB 恒定、误差 0.81%。16384 个寄存器存最大 rank——只回答"大约多少"。

Geo

ZSet 的位置封装 · 非独立类型

经纬度编码成 52 位 geohash 当 score；半径查询 = zset 粗筛 + Haversine 精算。

Stream

第六种类型 · 5.0+

消息日志 + 消费组：rax 索引、listpack 块、PEL 记录"已投未确认"——不丢消息的队列。

结构页

共享的底层资料室

SDS

src/sds.h · 简单动态字符串

C 字符串的三个痛点、len/alloc/flags 三字段、预分配与惰性释放、五种头部选型。所有 key 与绝大多数 value 的容器。

robj

src/object.h · 16 字节对象外壳

每个 value 的统一包装：type / encoding / lru / refcount / ptr；共享整数 0~9999；「编码 × 结构」全景图。

dict

src/dict.c · 哈希表

主键空间与 hash / set / zset 大对象的骨架；负载因子翻倍、progressive rehash 为什么「一桶一桶搬」。

listpack

src/listpack.c · 紧凑编码

连续内存、1~9 字节一个条目、backlen 逆向遍历；ziplist 连锁更新为什么被它根治。

阅读路径

两种学习顺序

自上而下（推荐第一遍）

先类型、后结构——把自己当「Redis 用户」，认识每个类型的命令与编码切换，再看它的内核。

string → list → hash → set → zset，然后随兴趣跳到 internals/sds，再 obj → dict → listpack。

自下而上（第二遍）

先底层、再类型——把自己当「数据库实习生」，先掌握每个独立结构的能力边界，再进入类型页看它被组合成什么。

顺序：sds → obj → dict → listpack，再回 string → list → hash → set → zset。

三条贯穿全笔记的线索
  • 「两阶段」：hash / set / zset 都是小→紧凑编码、大→高速结构，且单向不缩回。
  • 「单线程的优雅」：dict 的渐进式 rehash、listpack 的零连锁更新——所有操作都可暂停、可小步走。
  • 「省内存的决心」：listpack 一个数字 1 字节、intset 一整数 8 字节、共享整数 0~9999 一份——如果 Redis 里被反复提到「指针是贵物」，那是因为它住在内存里。
