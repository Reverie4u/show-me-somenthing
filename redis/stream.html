Redis · Stream

Stream —— 第六种类型,消息日志

Redis 5.0 引入的真正新类型(type=OBJ_STREAM):一条只追加的消息日志,每个条目有全局 ID(毫秒时间戳 + 序号),自带消费组——多消费者分工、内存记录"已投未确认"、可精确回溯。官方给消息队列场景的推荐方案。

PART 01 · 是什么

事件日志:序号 + 交付跟踪

命令概览

命令作用（一句话）
XADD key [maxlen …] id field val…追加一条消息;ID 缺省用 *(自动:毫秒 + 同毫秒内自增序号)
XRANGE / XREVRANGE key [id1 id2] [COUNT n]按 ID 范围读取(可空区间取全部);XRANGE 是正、XREVRANGE 是倒
XLEN key消息条数(快:stored 统计位)
XREAD [COUNT n] [BLOCK ms] key id单消费者读:从"上次的 ID"求增量,支持阻塞;多 key 同时读
XREADGROUP GROUP g c [COUNT n] [BLOCK ms] key id消费者组读:同一组内消息只被投递一次;ID 用 >(新消息)或任意 ID(重读 pending)
XACK key g id…确认已处理——移出 PEL(已投递未确认表)
XPENDING / XCLAIM / XAUTOCLAIM查看 PEL / 认领超时未 ack 的消息(7.0 起 XAUTOCLAIM 更简洁)
XDEL / XTRIM / XGROUP CREATE按 ID 精确删除 / 按 MAXLEN 裁剪 / 开组
ID 的双重角色:ms-seq(如 1699999999999-5)既是唯一的"消息编号",又是"时间顺序标签"——XADD 一个 * 就配好了;客户端也可以传自己的 ID(单调即可)。这让"断点续读"变成一条命令:XREAD key last_id。
PART 02 · 存储

rax 索引 + listpack 块

一棵索引树管住一整片 listpack

Stream 的结构是 redis 对象里"最接近数据库"的：列表块 + 索引 + 元信息三明治。数据本身躺在按批次打包的 listpack 里(每块默认 100 条消息),一个 rax(基数树)按 ID 索引到每一块。

结构草图
stream元信息
raxID 索引树
listpack₁≤100 条
listpack₂≤100 条
↑ 一级数据是"块",索引是"树"。这样 ID 定位 O(log 块数),块内线性;7.0 起块编码是 listpack(之前是 ziplist)——为什么不是一条消息一次 malloc?正解:消息都是小 KV,一个 block 里 100 条,内存与查找的成本都最小化
元信息里存什么
  • 消息总数(让 XLEN 是 O(1))与最大 ID ——读者一眼看到"到哪了"
  • 消费组列表(组名 → 组结构):组里记录 last_delivered_id(下一条新消息的位置)
  • 每个组的 PEL(Pending Entries List):"已投给消费者但还没 XACK"的消息 ID 表——这是"消息至少一次"语义的全部底气
  • 每个消费者在 PEL 里的所有权标记
牺牲点:Stream 不自动删已读消息——它是日志(只追加)。想"处理完就丢",用 XTRIM MAXLEN ~ 5000 或 XADD MAXLEN(近似裁剪,效率高)。
PART 03 · 消费

消费者组:分工 + 断点重来

三步流水线

1

开组

XGROUP CREATE events workers $(从新消息开始)或 0(从头)——组内所有消费者共享"还投给谁"的一张发报表

2

读

XREADGROUP GROUP workers alice COUNT 10 BLOCK 5000 key >——新消息只被组内一人拿到(round-robin 顺序),失败重试不会重复投出……

但注意:进程崩溃后,PEL 里它的消息还在——这就是"至少一次"的来源
3

确认

XACK events workers 1699999999999-5——从 PEL 删除。被 ack 过的消息才算"已消耗";超时未 ack 的,XAUTOCLAIM 认领给别的消费者重试

为什么这个"组"重要
投递但没有 ackPEL 表组内每个消费者记一笔
崩溃恢复XPENDING → XAUTOCLAIM超时消息认领重投,不丢
↑ 对比 List 队列的 BRPOP:弹出即"消失",崩溃即丢。Stream 把"消费发生"与"处理完成"分开成两件事——这是它作为消息中间件的核心卖点。
PART 04 · 对比

Stream 与 List 队列的取舍

List 当队列Stream
投递LPUSH + BRPOP，取出即删XADD / XREADGROUP，取出仍在(可重读)
确认无——"弹出"就是确认XACK，PEL 记录待确认
失败恢复丢消息XAUTOCLAIM 转移给他人
回溯不可XRANGE 精确到 ID(日志意义)
成本极轻(quicklist)重一档(rax + PEL 表)

什么时候用 List

简单任务队列

"老板派活、干完走人"：pop 就是交付，不需事后检查、不用重放。消息丢了认了。

什么时候用 Stream

事件流 / 消费组

多消费者分摊任务、业务侧要补偿重试、要"一份日志"可重放记账、或者推送数据流(XADD+XREAD BLOCK 就是精悍的 pub/sub)。
