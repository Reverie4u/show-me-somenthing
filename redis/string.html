Redis · String

String —— 最常用的数据类型

用户视角的「字符串」：SET 一个值、GET 回来，可以存储任意字节（文本、图片、序列化对象），还能当整数自增。底层它有三种编码（int / embstr / raw），其中两种直接建立在 SDS 之上。

PART 01 · 是什么

Redis String 概述

这是什么样的数据类型

Redis 五种数据类型里，String 是唯一没有「集合」语义的：一个 key 对应一个 value，value 是任意字节序列。

二进制安全

任意字节 · 含 \0

真实边界由长度而非终止符界定，所以 \0、图片、序列化对象、加密数据都能原样进出，不会中途截断——这是 SDS 赋予的（见 PART 03）。

上限 512 MB

单个值最大 512 MB

受客户端协议 proto-max-bulk-len（默认值即 512 MB）限制——官方文档以此作为单值大小的上限。

可作为整数

INCR / DECR 家族

值若长成合法整数（≤ 20 字符），会以 long long 形式存储并直接运算——见 PART 02 的 int 编码。

命令族速览

每条命令一句话：先混个脸熟，用它时知道「有这玩意」就够了。深浅细节（选项、边界情况）查命令文档。

命令作用（一句话）
基础读写
SET key value设值；EX/PX 过期时间、NX/XX 条件写都在这个选项里
GET key取值；不存在返回 nil
GETSET key value设新值并返回旧值，原子；6.2+ 基本被 SET key value GET 取代（后者还能同时带 EX/PX 过期）
批量
MSET k v k v …一次设多个值，原子；比 n 次 SET 少 n-1 个 RTT
MGET k k …一次取多个值；不存在的键返回 nil 占位
追加与截取
APPEND key suffix把 suffix 拼到 key 值的末尾，返回拼完后的总长度；key 不存在时相当于 SET key suffix（为何"反复追加也不慢"：涉及 SDS 预分配，见 PART 03 交互表与 sds.html）
STRLEN key返回字节数（不是字符数），O(1)
GETRANGE key start end截取子串；索引可为负（从尾部数）
SETRANGE key offset value从 offset 处覆写；越过的间隙补 \0
整数自增
INCR / DECR key整数值 ±1；值不是整数则报错
INCRBY / DECRBY key n整数值 ±n；若值还是 int 编码，全程不碰 SDS（见 PART 02）
位操作（字符串当比特数组）
SETBIT key offset 0|1置第 offset 位（offset 大时字符串按需增长）
GETBIT key offset读第 offset 位；越界返回 0
BITCOUNT key数「1」的个数；可限 [start end] 字节区间
BITOP AND|OR|XOR|NOT dst src…对多个值做位运算写进目标键（统计/合并类需求）
读取即清理（Redis 6.2+）
GETDEL key取值并删除——一条命令吃掉一次往返（GET + DEL）
GETEX key [EX s | PERSIST]取值，同时改或清除过期时间（EX/PX/EXAT/PXAT）；值本身不动
典型用途

缓存（最常见用法）· 计数器（自增原子性、DB 层的天然锁）· 分布式锁（SET k v NX EX，一条命令原子拿锁+过期）· 会话 token · 位图统计（每月活跃用户）· 限速器。另外注意：整个 Redis 的 key 天生就是字符串——类型里藏着一个「副业」：每个类型页都会提到它。

PART 02 · 编码

三种编码：INT / EMBSTR / RAW

值创建 / 修改时的一条判定链

同一个 SET k v，Redis 先对 value 做形态判断再决定「存成什么」，全程对调用者透明。

编码值形态触发条件value 内存
int long long 整数 合法整数表示（无前后缀 +/前导 0），长度 ≤ 20 不用 SDS，零额外分配，整个对象 16 字节（最快）
embstr SDS（短字符串） 字符串，长度 ≤ 44 字节 头 + 数据同块，一次 malloc（省一次分配）
raw SDS（长字符串） 字符串，长度超过 44 字节 头 + 数据分离，两次 malloc
PART 03 · 与 SDS

String 与 SDS：类型与实现

String 是语义类型（redisObject type = OBJ_STRING），SDS 是字节载体。二者常被混称——本节拆开讲清楚；SDS 的具体实现细节见 internals/sds.html。

两个层次，一条路径

String 是 Redis 文档里的语义类型——你 SET/GET 的那个值；SDS 是它在内存里的载体。名字里都有「字符串」，一个活在命令层，一个活在字节层。以 SET hello "world" 为例，一个值从命令落到字节，要穿过四层：

命令层
SET hello "world" String 类型此刻只是一段协议参数 —— 命令分派按 type 走到 STRING 命令族
↓ 协议解析后：命令名、key、value 全部成为 SDS
逻辑层
robj，type = OBJ_STRING 数据库里「这是一个 String」—— 语义与实现的官方分界线。16 字节外壳见 robj
↓ 创建 / 修改时，按值的形态选一种编码（PART 02）
编码层
int / embstr / raw 同一个 String 的三种内存形态 —— OBJECT ENCODING 返回的就是它
↓ embstr / raw 的 ptr 指向一块 SDS；int 的 ptr 就是值本身
物理层
sdshdr8 { len · alloc · flags } + "world"　或　(void*)42 字节真正待的地方 —— len 的 O(1)、预分配、五种头部都在 sds.html

key 恒为 SDS

String 类型只管 value

从协议参数到 dict 查找，key 一路都是裸 SDS —— 没有编码之分、不包 robj，就是一段二进制安全的字节序列。所以「String 用 SDS」严格说是「value 大多用 SDS」，key 则是 100% 用。

value 大多为 SDS

三种编码，两种是 SDS

embstr / raw 直接就是「robj + SDS」的组合；int 编码是唯一的例外——它把 long long 塞进指针，连 SDS 都没有。这正是「String」与「SDS」不能划等号的原因。

SDS 不止服务 String

通用字符串结构

命令名比较、list / hash / zset 的元素、AOF 缓冲区、客户端输入输出缓冲，全用 SDS。String 类型只是它最大的客户，不是唯一客户。

命令String 层的语义与 SDS 的交互
SET k v 判定 INT / EMBSTR / RAW，构造 robj embstr / raw 用 sdsnewlen 分配并拷贝数据
GET k 从 ptr 读出值回包 embstr / raw：直接从 buf 拷出；int：把 ptr 里的数值直接格式化成数字串回包
STRLEN k 返回「字符串长度」 不用扫描：SDS 直接读 len，O(1) —— 这是 SDS 的招牌能力
APPEND k s 如果值还是 int 编码，先拉回字符串 sdscatlen 追加 → 触发 sdsMakeRoomFor 预分配扩容
INCR k 等价于「读整数值 → +1 → 写回」 int 编码下完全不碰 SDS：直接操作 ptr 里的 long long
PART 04 · 延伸

追问四则

1embstr 为何以 44 为界?

16 字节 robj + 3 字节 sdshdr8 + 44 字节数据 + 1 字节 \0 = 恰好 64 字节。这四块内容由同一次 malloc 一并分配,总量正好落在 jemalloc 的 64B size class——零内部碎片、整块连续。官方源码注释说的正是这件事:44 是"还能整体装进 64B arena"的最大值。

超过 44 字节后,embstr 反而暴露缺点:APPEND 等写操作会触发整块重分配(因为头与数据绑死在一起,且对象本身不可变)。于是大值直接用 raw——头与数据分开,可以各自增长。

  • embstr 一次性分配:robj + SDS 头 + 数据 三合一,总尺寸固定。
  • raw 两次分配:robj 单独;SDS 头 + 数据 另一次,SDS 可独立扩容。
2int 编码的判定与不稳定

判断过程严格到苛刻:长度 ≤ 20 字符(LLONG_MAX 的字面长度)→ string2ll 严格校验 → 通过则 encoding = OBJ_ENCODING_INT。于是 SET n "12345" 存进去的不是字符串,是 long long:值直接塞进 robj 的 ptr 字段,INCR / DECR 家族直接操作这个整数,全程不碰字节数组——这就是自增命令快得离谱的原因。

int 编码不稳定:APPEND、SETRANGE 这些写入需要字符串形态,会把它「拉回」SDS(经 dbUnshareStringValue 变 raw / embstr),且不会再降级回 int。而 GETRANGE、STRLEN 是纯读取:int 值直接按数位截取 / 数位计数,对象不动。所以 OBJECT ENCODING 看到的 int 只是「当前时刻的快照」。

补一句:key 永远是裸 SDS。没有编码之分,就是一段二进制安全的字节序列——细节见最后一问。

Qrobj 是什么？和 String 什么关系？

robj（Redis Object）是每个 value 的 16 字节外壳：type（语义类型=OBJ_STRING）+ encoding（INT / EMBSTR / RAW）+ lru + refcount + ptr。String 是 type，SDS 是 ptr 指向的东西，三者是三层概念：String（类型）→ robj（外壳）→ SDS（载体）。

外壳帮 Redis 统一处理所有类型：命令分派看 type、内存淘汰看 lru、共享小对象看 refcount、不同编码看 encoding。完整结构见 internals/obj.html。

Q为什么 key 没有编码、永远是一段字节？

因为 key 的语义就是「一个名字」。名字不需要语义类型——没人对 key 做 INCR、APPEND，它的全部职责是参加哈希、精确比较、被过期，这些恰好是裸 SDS（字节数组 + len + 二进制安全）的强项。

  • value 需要花哨（数字、长短、编码选择），所以有 robj + 编码层；key 需要朴素，所以只有 SDS。
  • 代价是：key 必须永远保持「可比对的字节串」——查找时要算哈希、逐字节比较，没有 int 那种「值即指针」的捷径；而 value 是取到对象之后才谈语义，形态可以多变。

这也化解了一个常见困惑：key 虽然长得像字符串，但不属于 String 类型——它没有 type、没有编码、没有 robj 外壳，只是 keyspace 这张 dict 的一个键名（dictEntry.key），底层是一块 SDS。value 是 list 还是 zset 都与它无关：key 永远是这么一块「名字」。
