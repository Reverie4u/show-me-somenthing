Redis · List

List —— 两端 O(1) 的队列

有序、可重复的元素序列，头部压入头部弹出秒速 O(1)。它靠 quicklist 实现：双向链表做骨架，每个节点内嵌一块 listpack——两端 O(1) 由链表保证，批量压缩由 listpack 保证。

PART 01 · 是什么

List 概述

有序、可重复、双端操作

与 set 的区别：有顺序、可重复；与 zset 的区别：顺序由 push 顺序决定，没有 score。它天生是「队列」（FIFO）和「栈」（LIFO）的形状。

语义命令
压入（两端）LPUSH（头）· RPUSH（尾）· 支持多条，按序压入
弹出（两端）LPOP · RPOP · LPOP key count（批量）
范围 / 索引LRANGE（含两端，支持负数索引）· LINDEX · LLEN
修改LSET · LINSERT · LTRIM · LREM
阻塞版本BLPOP / BRPOP（空时休眠，超时或数据到达唤醒）· BLMOVE
阻塞命令是 List 在 redis 生态里的杀手锏：消息队列最怕的是「忙等轮询」。BLPOP 让客户端「睡着」等数据——底层是 Redis 监听的 key 事件（每个 key 一旦被阻塞等待，就进入服务器维护的「阻塞客户端表」），用一条命令≈删掉一半自研队列代码。
PART 02 · 编码

quicklist：链表的骨架，listpack 的血肉

唯一编码：quicklist

list 没有「小 list 用小编码」之分——统一 quicklist。历史上 quicklist 里也装过 ziplist（Redis ≤ 6.x），7.0 起内核换成 listpack。

三层结构
quicklist元
quicklistNode ⇄ quicklistNode ⇄ …双向链表
node
prev / next指针
entry → listpack一块连续内存
1st
[elem][elem][elem][elem][elem][elem][elem][elem]
↑ 整体：node 节点撑起 O(1) 的两端插入；每个节点内部是 listpack（一个元素最多 1~9 字节，见 listpack.html）——为什么不是「一元素一节点」？因为那样回到「每个元素一个指针」的老路；为什么不是一串 listpack？因为中间插入（LINSERT）和 LRANGE 是线性操作，链表给了常见的两端操作零成本。
为什么「小对象不用小编码」而用 quicklist？

list 的定位是「能长到 10 万条」，而 hash/zset 的 listpack 阈值是 128 条——list 若同样用「listpack → dict」路线，dict 版 list（双向链 + 随机）在两端操作上反而更差。于是 list 选了第三条路：listpack 一个装不下就再放一个 listpack（节点），链表只是节点之间的粘合剂——「链表 + 连续块」= 两端 O(1) + 高压缩率。

PART 03 · 配置

节点填充与压缩

两个旋钮：节点装多大、中间要不要压缩

配置默认值作用
list-max-listpack-size 128 每节点元素数上限（正数）。小了：节点多、链表长、遍历慢；大了：listpack 块太大、中间插入要搬内存昂贵。负数时按字节：-1 ~ -5 = 4 / 8 / 16 / 32 / 64 KB
list-compress-depth 0（不压缩） 两端留 n 个节点不压缩，中间节点用 LZF 压缩。压的是「很少碰的中间」——两端高频操作躲开解压 CPU 的代价，中间长列表占用内存锐减。深度 1：两头各留 1 个节点
这份「两端热、中间冷」的取舍是全页灵魂：quicklist 把自己暴露成了一对旋钮而非复杂接口——要么贪内存、要么贪两端速度，想调的人只有一个文件的口子。

复杂度一览

「list 是那种中间最惨的结构」

LPUSH/RPUSH/LPOP/RPOP O(1)；LINDEX/LINSERT/LRANGE O(n)——中间段是「边走边数」,所以千万别把 LINDEX 当随机索引用。

访问模式

特点便是代价的对称面

两端进出开销固定（无论多长）；中间的节点从头数——所以 list 适合"最近 N 条""任务排队"，不适合"按序号随机取"。

PART 04 · 场景

使用姿势

场景与注意事项

都围绕"两端快、中间慢"的访问模型来用。

消息队列：LPUSH + BRPOP（生产者消费者） 栈 / 最近操作：LPUSH + LTRIM 只留最近 N 条 时间线：最新在前，LRANGE 0 9 取首页 顺序待办：RPUSH + BLPOP 排队
经典组合：消息队列 + 无界注意

生产者 LPUSH jobs data，消费者 BRPOP jobs 0（永久等待）。超过一个消费者的场景，用 BLMOVE 把消息先移到「处理中」列表,处理完再删，防止崩溃丢消息。注意：list 的队列无 TTL 自动清理——"取出即删"的机制由命令语义（POP）保证，跟 Redis 没有任何队列级别的自动兜底。

对比：Stream 在 Redis 5.0 入局——它给「消息队列」加了持久 ID、消费者组、ack 语义。List 至今仍负责「简单任务队列」，Stream 负责「复杂事件流」，二者边界在命令层,不在本页。
