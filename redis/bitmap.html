PART 01 · 是什么

把一个字节掰成 8 个位来用

位的世界里，一段 String 就是一张海量开关表

比如"用户 12345 今天是否活跃"——不用存一个用户 ID 集合，只需把第 12345 位设为 1。1000 万用户 1 个字节都不浪费：1000 万 bit = 1.25 MB，而存 1000 万个元素 ID 的 set 要 100 MB 量级。

内存形态：一个 key 就是一句话的二进制位
bitmap key（String / SDS）… 0 1 0 0 1 1 0 1
offset0
offset1
offset2
…
↑ 每个 offset 是 string 里的第 N 位(第 N/8 字节的第 N%8 位)。offset 范围 0 ~ 2³²-1 ——所以单个 bitmap 最大 512 MB,与 String 上限一致(根源相同)。
命令作用（一句话）
SETBIT key offset 0|1置第 offset 位；offset 大时字符串自动按需增长
GETBIT key offset读第 offset 位；超出范围返回 0
BITCOUNT key [start end]数「1」的个数；可限定字节区间(配合每天位图很常用)
BITPOS key 0|1 [start [end]]找第一个 0/1 的位置——求「最早出现」
BITOP AND|OR|XOR|NOT dst src…多个位图做位运算写进目标键：多天并集、交集就是这么算的
BITFIELD key get|set|incrby …按「字段式」访问位区间(把位图当定宽整数数组,如每 8 位一个计数)
PART 02 · 场景

每日活跃与复合统计

经典打法：一天一张位图

最常见也最朴素的设计:每用户固定一个 offset(user id 映射到 0 ~ N-1),每张活跃统计一个 key。

1

记录每日活跃

SETBIT act:2026-08-01 12345 1(用户 12345 当天访问);无访问的位保持 0——不用写。

2

统计单日

BITCOUNT act:2026-08-01 → 当日活跃人数。1.25MB 的位图,一次即可。

3

统计复合区间

BITOP OR act:week:31 act:2026-08-01 act:2026-08-02 … act:2026-08-07 → BITCOUNT 出「本周活跃」;7 月 → 31 天。

内存账本(1000 万用户)
每日位图10,000,000 bit= 1.25 MB
一年365 × 1.25 MB≈ 456 MB
同一数据的 set1000 万 ID≈ 100+ MB / 天
↑ 省 80 倍起步；且能直接做位运算（并集/交集），不用把数据捞到客户端算。
用户 id 怎么映射?——两个常见方案：① 自增 id 直接当 offset(0 起始);② 已存在百万级用户时,`SETBIT` 前先查一个 db 自增映射。无论如何,关键是 id → offset 的映射要稳定。
PART 03 · 与 String

底层就是 SDS，别无他物

一切复用 String 的存储

BitMap 不是 `type` 一枚值(没有 OBJ_BITMAP)——它从头到尾就是 type=STRING 的 value,占着 SDS 的内存,只是"命令解释器"换成了认识位的。

普通 StringBitmap 视角下的同一个值
OBJECT ENCODINGINT / EMBSTR / RAW一样。位操作会直接把 int/embstr 转 raw
（需要随机字节写入）
底层结构SDSSDS
最大体积512 MB2³² bit——来自同一个 proto-max-bulk-len 限制
边界二进制安全位即字节,天然安全——所以位图就是"人话版本"的二进制字符串
什么时候别用位图
  • 稀疏数据：如果说 1 亿用户里只有 138 个活跃,SETBIT key 99999998 1 会瞬间把 key 撑到 12.5 MB(offset/8)。稀疏时用 set / HLL 更宜。
  • 需要精确"交集"而用户量大：BITOP OR 对 7 个 1.25MB 值是 8.75MB 拷贝,内存反而贵。备选:BITFIELD, 或在应用侧 "先设 BITCOUNT 粗筛"。
  • 无法与 HyperLogLog 混用：bitmap 是"精确的成员判断",HLL 是"近似的基数估算"——一个是地图,一个是计数,别混。
