Redis · Hash

Hash —— 字段级操作的映射

一个 key 装着 field → value 的映射，是 Redis 里最接近「对象」的表达。它有两级编码：小对象（≤128 字段且值小）用 listpack 一块连续内存塞进去；大对象切换到 dict，换来 O(1) 的单字段查改。

PART 01 · 是什么

Hash 概述

一个 key 一张小地图

「field 是纵向的、value 是行」——没有全局 key(list 的元素可重复、hash 的 field 唯一)、字段独立可动。

语义命令

提醒：hash 的 value 与 string 的 value 同规格——任意字节、可数字自增。hash 真正不同于 list/set 的是「字段级」那三个字：一次只改一个字段，网络往返与内存拷贝都按字段大小量级,不做全对象序列化。
PART 02 · 编码

listpack → dict：一次「升级」

切换阈值与方向

创建时是小对象（连续内存，listpack）；字段 ≥ 128 个或任一字段值 ≥ 64 B 时，自动换成大对象（dict）。转变单向、不可逆。

PART 03 · 为什么

两阶段设计的本质

为什么不能只用 dict

直接回答：小 hash 用 dict 会亏在三处——

1. 常数成本不对称

哈希也不是零成本

dict 查一个字段 = 算哈希 + 桶位 + 链扫，而 listpack 内几个字段就是……线性扫下一个内存。n=3 时谁的「O(1)」更快，没有悬念。

2. 哈希序不可预期

listpack 是稳定的插入序

HGETALL 的返回顺序 listpack 版本是插入序（可预期、可依赖），dict 版是哈希序（依赖哈希函数与 rehash 状态）。对做「散列展示」的客户端，前者白送的可预期性。

3. 每字段的固定开销

dictEntry + robj + 两个对象

dict 版每字段：dictEntry（指针若干）+ robj（16 B）+ key SDS + value SDS，3 个字段的 hash 至少 ~90 字节；listpack 版同样的 3 字段约 18 字节。这是数量级差异，不是常数差异。

为什么不缩回（单向转换）

因为 listpack 的「重建」= 重新遍历 + 判断 + 重新编码、dict 的「缩回去」= …… 有没有那个编码,源码里都没有实现「dict → listpack」的回程。设计取向:hash 变大的趋势一旦触发,就给它定「大 hash 一生」——回不到小对象编码,省掉了「频繁振荡」的兑换退路。

同款翻版：zset 同样「listpack → skiplist+dict」单向；set 的 intset → dict 单向。一个模式:小→大承诺不可逆,用「容忍小对象稍慢」换「省掉反向迁移逻辑」。

PART 04 · 场景

使用姿势

场景与注意事项

都围绕"字段级读写、局部更新"这个特点。

用户对象缓存（比 JSON 字符串快） 商品字段集（可变字段） 计数器分组（HINCRBY 按字段） 稀疏属性（大部分用户只有少量字段）
为什么「Hash 存对象」优于「JSON 字符串存对象」
  • 读单个字段：hash 走 HGET 只取一个字段;JSON 版要 GET + 反序列化整个对象 + 自己 cut。
  • 改单个字段：hash HSET 原地;JSON 版 GET 全量→改→SET 全量（网络 + CPU 双浪费）。
  • 前提:字段都是独立同源、值小。若对象是「整体读写型」或者字段很大(10MB 图片),hash 反而没有优势——字段值本质还是字节。

注意：hash 的 field / value 仍是「字节串」——语义与 String 类型相同（你甚至能对字段值做小字符串处理）。区别只在容器:小值以裸字节内嵌在 listpack 里,不包 robj;大值则在 dict 侧以 robj 挂在字段上。所以 hash 省也不是没有代价,省在「不经过 robj 那一层」。
